# graph-creativity

Песочница для графовой модели повышения креативности предприятия.
Реализует минимальный каркас из `~/docs/reports/master/model/karkas.tex`:
11 вершин, 16 дуг, дискретная динамика с запаздываниями, критерий
`k(P) = R(P)/C(P)`, минимальные достаточные наборы, критические меры и
критические комбинации событий.

В приложении два режима: **ЛПР** (анкета, бюджет, рекомендация) и
**Исследователь** (все подмножества, σ₁, редактирование графа).

## Быстрый старт

```bash
python3.13 -m venv .venv
.venv/bin/pip install -r requirements.txt

# Streamlit-песочница
.venv/bin/streamlit run app.py
```

Открыть `http://localhost:8501`.

CLI:

```bash
# один план и сценарий -> CSV + PNG
.venv/bin/python -m graphcreativity run --plan hybrid --scenario nominal

# все подмножества мер -> минимальные достаточные наборы, критические
# меры, критические события, Парето-фронт
.venv/bin/python -m graphcreativity compare --scenario nominal

# топология графа
.venv/bin/python -m graphcreativity graph
```

Если установить пакет (`pip install -e .`), доступна команда `gcm`.

## Что получается на выходе

`run` создаёт каталог `out/run/`:

- `dynamics.csv` — месячные ряды: нормированные и физические `X`,
  профили мер `u_j`, сценарий `Y`, `σ_i`, `R`, `C`, `k`;
- `dynamics.png` — четыре панели: целевой `X1` в % к базе, все `X`
  в нормированном виде, профили мер, `R/C/k`;
- `indicators.png` — small multiples по каждому показателю в его единицах;
- `summary.json` — `T_goal`, `x1(T)`, затраты, эффект, `k`, параметры.

`compare` дополнительно пишет `plans.csv`, `plans.png` и `summary.json`
со списком минимальных достаточных наборов, критических мер и критических
комбинаций событий.

## Модель

Все показатели `X` нормированы: `x=0` — база, `x=1` — цель, `x>1` —
перевыполнение. Для «меньше — лучше» (`X3`, `X7`) рост `x` означает
снижение физического показателя.

```
σ_i(t) = Σ_p w_pi · a_p(t − τ_pi)
x_i(t+1) = x_i(t) + λ_i·(x_max − x_i(t))·[σ_i − θ]_+ − μ_i·x_i(t)
λ_i = ln 10 / τ_i_rise
```

`a_p` — состояние показателя, профиль меры `u_j(t)` или отклонение
сценария `Y`. Меры задаются ступеньками: старт, длительность,
интенсивность. Стоимость по умолчанию списывается один раз в месяц
запуска (`cost_mode: one_time`).

### Важные соглашения и известные расхождения с документом

1. **Потолок насыщения.** В `karkas.tex` v1.2 уравнение исправлено на
   `(x_max − x_i)`: при буквальном `(1 − x_i)` точка `x=1` была асимптотой
   и цель `x1(T) ≥ 1` недостижима ни при каком плане. Исторический режим
   `strict` оставлен в ПО только для демонстрации этого артефакта.

2. **Порог.** `θ=0.42` — демонстрационное значение, а не результат статьи.
   При нём воспроизводятся два минимальных достаточных набора `{m1,m3}` и
   `{m3,m4}`, одиночные меры недостаточны, а `{m1,m4}` — «почти»
   (x1(T)≈0.95). При `θ=0.30` одиночная `m1` уже достаточна, но только к
   36-му месяцу; при `θ=0.31–0.40` наборов три; при `θ=0.425` `P1` не
   проходит. Это чувствительность, а не подгонка: см.
   `out/thesis/theta_sensitivity.*`.

3. **§5 — статика, а не динамика.** Числа `σ1 = 0.61, 0.77, 0.35, 1.12,
   1.38, 0.96` равны сумме путей длины ≤ 2 от мер к `X1`. Это
   реализовано отдельной функцией `effect_strength` и проверяется тестом;
   с динамикой уравнения (1) они не совпадают. В `karkas.tex` v1.2
   статический столбец дополнен динамическими `x1(T)`, `T_goal`, `C`, `k`,
   которые генерируются скриптом, а не набираются руками.

4. **Полярность `Y5`.** В конфиге `Y5` — «дефицит квалификации»: рост
   `Y5` ухудшает ситуацию, поэтому дуга `Y5→X3` остаётся `−0.35`, как в
   документе. `Y3` — «рыночное давление»: рост `Y3` ухудшает `X1`.
   `Y2` — доступность грантов: рост `Y2` увеличивает `X4`, сокращение
   задаётся отрицательным значением (`grant_cut: Y2 = −0.4`).

5. **Базовые и целевые значения `X2`, `X4`, `X7` — иллюстративные.**
   В `karkas.tex` для них заданы только единицы и роль в модели; числа
   `20→35 %`, `2.5→5 % выручки`, `1000→960 руб./ед.` поставлены для
   наглядности, а не взяты из статьи. Для `X1` база 100 и цель 125 —
   это и есть «+25 % за 36 мес.».

6. **Бюджет входит в определение достаточности.** `minimal_sufficient_sets`
   по умолчанию требует одновременно `reached and feasible`: набор,
   который достигает цели, но стоит дороже бюджета, не считается
   допустимым решением. Для диагностики можно вызвать
   `minimal_sufficient_sets(rows, require_feasible=False)`.

7. **Критические меры и критические события — разные объекты.**
   `critical_removal_sets` отвечает на вопрос «удаление каких мер ломает
   полный комплект»; `critical_event_combinations` перебирает атомарные
   неблагоприятные сценарии (`market_downturn`, `low_qualification`,
   `grant_cut`) и находит минимальные комбинации, при которых план
   перестаёт достигать цели. `robustness_radius` — сколько одновременных
   событий план выдерживает.

8. **Ответственные за меры.** У мер есть поле `owner`; оно попадает в
   рекомендацию и в редактор графа. Без ответственного мера не должна
   попадать в итоговое решение, но расчёт её не блокирует.

9. **`k` — критерий только для допустимых планов.** Если цель не
   достигнута или бюджет превышен, `k = R/C` в таблицах и KPI не
   показывается: иначе дешёвая, но не достигающая цели мера выглядела бы
   «эффективной». В `summary.json` сырое значение остаётся для диагностики.

## Что смотреть в Streamlit

- **Режим ЛПР** — верхний блок: KPI выбранного плана, бюджет, приоритет
  выбора («эффект/затраты», «время», «стоимость»), рекомендация с
  ответственными и стартами, устойчивость и таблица альтернатив.
- **Динамика** — `X1` в % к базе, все пять показателей в нормированном
  виде, профили мер и экономика.
- **Показатели** (режим исследователя) — те же ряды в физических единицах.
- **Сравнение планов** — сначала именованные планы с их собственными
  стартами (строка выбранного плана совпадает с KPI), затем все 2³
  подмножества мер с нулевыми стартами, минимальные достаточные наборы,
  критические меры, критические комбинации событий, Парето-фронт,
  матрица план×сценарий и (по галочке) устойчивость всех подмножеств.
- **Сценарии** — веер траекторий `X1` по всем сценариям среды, запас
  `x1(T) − 1` и радиус устойчивости.
- **Граф** — топология с весами и знаками дуг плюс редактор: таблицы
  вершин (включая ответственного) и дуг, добавление/удаление вершин,
  правка весов и задержек, экспорт YAML.
- **Данные** — таблица рядов и выгрузка CSV/JSON.

В режиме ЛПР скрыты отладочные `μ`, `x_max`, `gain`, режим насыщения и
σ₁; они остаются в режиме исследователя. Слайдер `θ` и бюджет доступны
обоим режимам: это не «отладка», а параметры решения и чувствительности.
Например, при `θ=0.45` набор `{m3,m4}` перестаёт достигать цели, при
`θ=0.30` одиночная мера `m1` уже достаточна (но только к 36-му месяцу),
а при бюджете 45 млн `{m3,m4}` (50 млн) выпадает из допустимых наборов.


## Воспроизведение чисел ВКР

```bash
# таблица §5, θ-чувствительность, матрица план×сценарий, рекомендация
.venv/bin/python scripts/reproduce_thesis.py

# те же файлы сразу в каталог модели, откуда их читает karkas.tex
.venv/bin/python scripts/reproduce_thesis.py \
  --out ~/docs/reports/master/model/generated
```

Скрипт пишет `section5.tex` и `theta_sensitivity.tex` (их подключает
`karkas.tex` через `\input{generated/...}`), а также CSV и
`recommendation.md`. Числа в тексте должны браться из этих файлов, а не
набираться руками. `karkas.tex` компилируется из каталога `model/`:

```bash
cd ~/docs/reports/master/model
pdflatex karkas.tex && pdflatex karkas.tex
pdflatex protocol.tex && pdflatex protocol.tex

cd ~/docs/reports/master
pdflatex main.tex && pdflatex main.tex
```

## Тесты

```bash
.venv/bin/python -m pytest -q
```

Покрыто: совпадение статической `σ1` с таблицей §5, два минимальных
достаточных набора при θ=0.42, появление `{m1}` при θ=0.30, исключение
`{m3,m4}` при бюджете 45 млн, различие critical removal sets и critical
event combinations, per-node θ и его перекрытие явным `SimOptions`,
использование собственных стартов именованного гибрида, недостижимость
цели в `strict`-режиме, задержка отклика, устойчивость гибрида к
сценариям, запуск Streamlit без исключений, применение правок через UI и
сброс, сборка модели из таблиц редактора, удаление вершин с каскадом
дуг/планов/сценариев и round-trip YAML.

## Как менять модель

### В UI

Вкладка **«Граф»** — полноценный редактор:

- таблица вершин: название, короткое имя, единица, направление,
  база/цель/`rise` для показателей, стоимость и ответственный для мер,
  координаты на схеме;
- таблица дуг: `из → в`, вес `w`, задержка, признак опциональной дуги,
  класс и механизм; строки можно добавлять и удалять;
- добавление вершины (показатель, мера или фактор среды) и удаление
  вершины вместе со связанными дугами;
- кнопка **«Применить изменения»** пересобирает модель и пересчитывает
  все вкладки;
- **«Скачать YAML»** сохраняет последнюю валидную модель на компьютер;
  **«Сохранить в configs/»** записывает её рядом с исходным конфигом
  (при локальном запуске).

При удалении меры она исчезает из планов, при удалении фактора среды —
из сценариев. Целевой показатель `X1` удалить нельзя. Новый фактор среды
по умолчанию получает значение 0 во всех сценариях; его значения
задаются в экспортированном YAML. Экспортированный YAML не сохраняет
комментарии исходного `karkas.yaml`, но полностью загружается обратно.

### В YAML

Почти всё также можно менять в `configs/karkas.yaml`:

- добавить вершину: новый блок в `nodes` (`kind: indicator|measure|environment`);
- добавить дугу: элемент `edges` с `from`, `to`, `w`, `delay`,
  `source` (И/Э/Л/Н) и `mechanism`;
- добавить план: блок в `plans` (`measures: {m1: 0, m3: 3}`);
- добавить сценарий: блок в `scenarios` (`values: {Y3: 0.5}`,
  `atomic: true|false`; `false` исключает сценарий из перебора
  критических событий);
- поменять параметры: `model.version`, `model.theta`, `model.mu`,
  `model.x_max`, `model.gain`, `model.budget_max`;
- задать per-node параметры: `theta`, `mu`, `x_max` в блоке вершины;
  явный `SimOptions(theta=...)` перекрывает их для всего прогона;
- задать ответственного: `owner` в блоке меры.

Валидация не даст сохранить дугу в неизвестную вершину, петлю,
отрицательную задержку или дугу не в показатель. План дороже бюджета —
не ошибка структуры: он помечается `feasible=false`, а в UI
показывается предупреждение.
